635 - CR B1 step 2: the five moment sums, and G10 becomes true
===============================================================

All ten values now come out of the sweep and equal
`aggregate.moments_per_component` exactly. The expected failure that
steps 0 and 1 shipped is green and its decorator is gone.

--------------------------------------------------------------------
WHAT WAS ADDED

`_sum_i` and `_sum_ii` IMPORTED, not reimplemented, exactly as the CR
requires -- two copies of a closed-form identity are two chances to
get the `(lo-1)*lo` term wrong, and a wrong second moment is not a
crash, it is a plausible centroid. They are imported INSIDE `sweep`
(`aggregate` imports `SweepResult` from `sweep`, so module level would
be circular) and bound to LOCALS, because the loop calls them once per
run and a local beats a global on the innermost path.

The five contributions sit in the same hoisted axis branch step 1
built, which is now the whole of the per-run work:

    row:  sx += s1          col:  sx += n*k
          sy += n*k               sy += s1
          sxx += s2               sxx += n*k*k
          syy += n*k*k            syy += s2
          sxy += k*s1             sxy += k*s1

`k` is the run's line. `sxy` is the ONE line that is the same in both
branches, which is the tell that it is the cross term.

Merged at the same three sites as the extents. Nothing else changed.

--------------------------------------------------------------------
G10, NOW THAT IT IS TRUE

Steps 0 and 1 deliberately did NOT write the contract down as a
guarantee, because it did not hold. It does now, so it is stated:

  G10  `moments` is `None` unless the caller asked, and when it is a
       dict it equals `aggregate.moments_per_component(result)`
       EXACTLY -- same keys, same ten integers, no tolerance. All ten
       are commutative monoids over the run set (integer addition, and
       min/max), so accumulating them during the sweep and merging
       them on union cannot change the answer, whatever the order of
       runs, the axis, or the merge sequence.

That last sentence is the reason this is a MOVE rather than a second
implementation, and it is why an approximate comparison anywhere in
its tests would be a category error rather than a loose tolerance.

--------------------------------------------------------------------
THE EXPECTED FAILURE DID ITS JOB

`test_moments_match_the_oracle` was marked `expectedFailure` in step 0
against an empty dict and stayed failing through step 1, correctly,
because it checks all ten fields and five were zero. When the sums
landed here, unittest reported an UNEXPECTED SUCCESS -- which it
treats as a suite failure -- and the suite stayed red until the
decorator came off. Step 2 could not have landed quietly, which is
exactly what the marker was for and what simply omitting the test
would not have given.

        GUARDS THE FOUR ABOVE FROM PASSING ON ZEROS. Every one of them
        is an equality against another computation, and `0 == 0` is an
        equality. This is not a hypothetical: steps 0 and 1 shipped

        It is the state the file was in one commit ago.

NOT CLAIMED

  * No measurement. Step 5. The hot-path concern flagged at step 1
    stands and has grown: at `moments=False` the run loop now
    evaluates `moms_of is not None` twice per run, and at
    `moments=True` it makes two Python function calls per run for the
    closed forms. The second is not new cost -- `_accumulate` pays it
    too, on the pass this replaces -- but the first is, and it is the
    2% the CR budgets.
  * `aggregate.py` still untouched. Step 4 is where
    `moments_per_component` starts using this, and where the second
    pass actually disappears for a caller that asks.
  * Nothing in the package passes `moments=True`. That is the
    capability-only scope that was chosen, not an oversight.
