1. x IS +6.177 bp ON EVERY RULE OF EVERY TABLE

Attributed by reading the PDF's own vertical rules and subtracting:

    table 1/2   PDF        54.155  123.202  155.398  204.602  670.499
                manifest   60.332  129.379  161.575  210.779  676.676
                delta      +6.177   +6.177   +6.177   +6.177   +6.177

    table 3     PDF        51.223  120.269  152.466  198.835  ...
                manifest   57.400  126.446  158.642  205.012  ...
                delta      +6.177   +6.177   +6.177   +6.177

CONSTANT, not proportional -- +6.177 at x=51 and +6.177 at x=676. So
it is an ORIGIN offset and not the TeX-point conversion 601 warned
about, which would grow across the page. 6.177 bp is 25.7 px at 300
dpi, which is the +26 in the table.

The cause is pdfdrill's to find, but the shape says where to look: a
constant added to x means the position was recorded relative to
something other than the paper's left edge. `\tabcolsep` defaults to
6 TeX pt = 5.977 bp, which is near but not equal.

2. THE LAST COLUMN RULE IS MISSING FROM EVERY TABLE

    table 1/2   PDF has 6 vertical rules (5 columns)
                manifest has 5 (4 columns)     rightmost 1136.396 absent
    table 3     PDF has 8 vertical rules (7 columns)
                manifest has 7 (6 columns)     rightmost 1169.510 absent

So the rightmost column of every table is never described and never
checked. That is why 142 cells were compared where 34 rows x their
columns would give more, and it is why the page-3 count reads 6
columns against the lattice's 7.

3. THE FIRST ROW OF EACH TABLE TAKES THE HEADER'S TOP RULE

This is the entire y residual. Two rows of 33 measured have |dy0| > 1:

    0049_EQ0001  page 1  dy0 -53     rule_above 693.051
    0049_FO0001  page 2  dy0 -52     rule_above 753.883

On page 1 the PDF's horizontal rules are 692.852, 680.498, 624.707 --
table top, under the header, table bottom. The lattice reads two rows:
header 622..671 px and data 674..904. EQ0001's `rule_above_bp` is the
TABLE's top rule, so its rect spans the header as well as the data
row, and the lattice's header row is left unmatched.

    every other row: |dy0| <= 1 and |dy1| <= 1

So the emitter is not accounting for the repeated header: the first
data row on a page inherits the rule above the header instead of the
rule below it.

THE THREE THINGS ASKED

  SEVEN COLUMNS. Table 3 has 7 column rules in the manifest and 8 in
  the PDF. The consumer handles it -- page 3's 30 cells are within
  1 px on both y edges and carry only the x offset shared with every
  other table. 602 validated 4, 5 and 6 columns; 6 and (in the PDF) 7
  behave identically. Nothing about the column count is a problem.

  THE PAGE-BREAK ROW. `0049_DIA_0006`, `rules_on_one_page: false`,
  above 87.082 and below 614.998 -- a "rectangle" 528 bp tall on an
  841 bp page.

    THE CONSUMER REFUSES IT. It did so already, but INCIDENTALLY: the
    two y values come from different pages and so are not ordered, and
    G5's ordering check caught the inversion. An incidental refusal
    stops working the moment the numbers happen to line up -- a row
    breaking near the top of a page would pass it.

    So `cell_rect` and `row_rects` now take `rules_on_one_page` and
    refuse by name (G7), with the reason in the message. Tested both
    ways, and deleting the guard fails the suite. The default is True,
    so every existing caller is unchanged.

  THE 27 ROWS ON PAGE 2. This is where a systematic offset would show
  and it did -- but not in the y:

    page 1  (4 cells)     y0 median -53.0    x0 median +26.0
    page 2  (108 cells)   y0 median  -1.0    x0 median +26.0
    page 3  (30 cells)    y0 median  -1.0    x0 median +26.0
    page 4                no cells (its only row is the refused one)

    26 of 27 page-2 rows are within 1 px on every y edge. The single
    outlier is FO0001, the first row, for the header reason above. The
    x offset is identical on all three pages and both column
    geometries, which is what makes it one bug rather than three.

    python3 tools/manifestcheck.py 0049

reads `pdfdrill-rows.json`, verifies the sha, refuses rows flagged

608 #3 CONTINUED - the working recipe for the header rule
====================================================================

The page must be in the label, confirmed, and `\thepage` is the one
that works. Measured on a two-page longtable with an `\endhead`:

  A LABEL INSIDE \endhead IS MULTIPLY DEFINED
      \zsavepos{hdr}          2 pages -> 2 definitions of `hdr`
                              "LaTeX Warning: Label `hdr' multiply
                              defined."

  \thepage FIXES IT
      \zsavepos{hdr\thepage}  labels hdr1, hdr2
                              0 multiply-defined, 0 errors

  \theabspage DOES NOT
      \zsavepos{hdr\theabspage}
                              both pages write `hdr0` -- the counter
                              reads 0 at contribution time -- and it
                              is multiply defined again. zref-abspage
                              is loaded and still does not help here.

AND THE POSITION MUST BE TAKEN IN A \noalign, NOT IN THE HEAD'S TEXT.

  \zsavepos placed in the header ROW records a baseline, and the
  baseline is not the rule:

      page 1   zsavepos 764.076 bp   nearest rule 772.644   -8.568
      page 2   zsavepos 764.076 bp   nearest rule 772.644   -8.568

  Eight and a half points below the rule it is meant to mark. In a
  `\noalign` immediately after the header's `\hline`, INSIDE
  `\endhead`, it lands on the rule:

      \hline A & B \\ \hline
      \noalign{\zsavepos{hdrule\thepage}}
      \endhead

      page 1   zsavepos 772.445 bp   nearest rule 772.644   -0.1993
      page 2   zsavepos 772.445 bp   nearest rule 772.644   -0.1993

      0 errors, 0 multiply-defined, labels hdrule1 and hdrule2.

THE RESIDUAL -0.1993 IS EXACTLY HALF A RULE (0.3985 / 2 = 0.19925),
so this records the rule's LOWER EDGE and the centreline 610 asks for
is that value plus `\arrayrulewidth / 2`. That is also the explanation
of 610's finding: the emitted y values are half a rule out because a
`\noalign` savepos sits at an edge, and 610's single outlier -- one
row at -0.199 where 32 were at +0.199 -- is a savepos on the other
side of its rule.

WHAT I DID NOT CONFIRM. That a `\noalign` placed AFTER `\endhead` is
discarded. In longtable's structure the material between `\endhead`
and `\endfoot` is FOOT material, so a savepos there records the foot
and the question does not arise in the recipe above -- the savepos
belongs inside the head, before `\endhead`. My attempt to test the
discard put the `\noalign` in the foot and recorded it twice, which
measures the foot repeating rather than the head discarding, so it is
reported as untested rather than as a refutation.

RE-RUN: the four probe documents are minimal longtables of 60 rows
over two pages; the recipe above is the only one of the four that is
simultaneously singly-defined, error-free and on the rule.
