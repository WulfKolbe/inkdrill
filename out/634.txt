--------------------------------------------------------------------
WHAT WAS ADDED

`moms_of: dict[int, list[int]]`, keyed by component ROOT, value a ten
slot mutable list in `Moments` field order. Same migration discipline
as the counter pair, at the same three sites:

  BIRTH    create the vector from this run alone
  ATTACH   add the run in; move the vector only if the root moved
  MERGE    pop both, combine elementwise, store under the survivor

A LIST, NOT A `Moments`. `Moments` is `frozen=True`, so accumulating
into it would allocate a new object per run -- roughly three million
per document. The frozen type is built once per component in the
assembly loop instead. This is written into the code comment because
it reads like something to tidy up and is not.

The axis test is HOISTED out of the run loop as `row_axis`. A run is a
contiguous span on one scan line, so on a row sweep it spans x from
`lo` to `hi` and occupies a single y, and on a column sweep exactly
the reverse. That is the only place the two axes differ, which is why
the CR isolates it in this step.

Assembly indexes `moms_of[c.root]`, NOT `.get(root, default)`. One
vector per current root is the invariant the migration maintains, and
a default would hand back a component of area zero -- a plausible
wrong answer, which is the exact failure mode CLAUDE.md records for
keying by `nodes[0]` instead of `root`.

`Moments` is imported INSIDE the function. `aggregate` imports
`SweepResult` from `sweep`, so a module-level import would be
circular; `aggregate.moments_of_runs` does the same with `raster`.

THE FIRST RUN KILLED ONLY 5 OF 7, AND THE SURVIVORS WERE THE PAIR THE
CR PREDICTED -- "wrong only for components that merge, so a fixture
set of isolated glyphs will not catch them". It was right, and the
reason is sharper than "isolated glyphs":

    only THREE (fixture, axis) pairs in the whole set contained a
    merge at all -- root_identity_trap/row, checkerboard/row,
    checkerboard/col

and in none of those did the LOSING component reach past the
survivor. That is not an accident of the fixtures, it is the usual
case: the first parent is the leftmost run on the previous line, and
the joining run has already been folded into the survivor, so the
survivor normally holds the extreme already. The merge min/max is
DEAD CODE on ordinary shapes and only fires on one specific geometry.

Two fixtures were designed for it. Both are the same idea -- a
component that is wide at the top, narrows to a single column, and is
met lower down by a second component nearer the joining run:

    merge_loser_reaches_left     merge_loser_reaches_right
        .####.                       ..####
        ....#.                       ..#...
        ..#.#.                       #.#...
        ..#.#.                       #.#...
        ..####                       ###...

    left:  the loser's x0 is 1, the survivor's is 2
    right: the loser's x1 is 5, the survivor's is 2

That killed three of the four merge branches. `y1` still survived, and
the reason is worth recording because it is a property of the sweep
rather than of the fixtures:

  ON A ROW SWEEP, `w[9] > v[9]` CANNOT FIRE. y1 is the maximum line,
  the survivor has just taken the CURRENT line, and every other run
  seen so far is on an earlier one. The branch is unreachable on that
  axis by construction. It fires on a COLUMN sweep, where y comes from
  the run's `lo..hi` instead.

The fixture set is row-shaped by history -- which is one of the CR's
own listed open assumptions -- so both merge fixtures were also added
TRANSPOSED, generated by `_transposed()` rather than hand-drawn, so
the correspondence is by construction and cannot drift. That killed
the fourth.

THE ONE SURVIVOR IS AN EQUIVALENT MUTANT, PROVEN NOT ARGUED.
`moms_of[rn] = moms_of.pop(rp)` -> `moms_of[rn] = moms_of[rp]` leaves
a stale entry behind. `rp` has just become a child and union-find
roots never become roots again, so nothing ever reads it. Verified by
digest rather than by reasoning -- 27 fixtures x 2 axes x 2 conns,
40 random masks, and a real 15.5 Mpx page:

    clean    27e2b40afc0fc5374d0dad0031d19f09cd996b1fa3bfab6215748ceb55d41c54
    mutated  27e2b40afc0fc5374d0dad0031d19f09cd996b1fa3bfab6215748ceb55d41c54

So no test can kill it and none should be written. IT IS NOT FREE,
THOUGH -- it is a memory leak, and the CR's step 5 measures memory.
Measured on p1:

    44,817 runs, 421 components
    attach root-moves: 739
    dict at the end: 421 live vs 1,160 with the leak = 2.76x

The root moves only when a component's second run attaches, so the
leak is bounded by root-moves rather than by run count. `pop` stays,
and step 5's memory number is where this becomes observable.
